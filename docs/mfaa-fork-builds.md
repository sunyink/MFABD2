# 可选的自家 MFAAvalonia 构建

常规构建继续读取 `requirements.txt` 中的 `MFAA_TAG`，从 `MaaXYZ/MFAAvalonia`
下载客户端。无需修改该文件即可临时选择自家客户端。

1. 在 `sunyink/MFAAvalonia` 的 `mfabd2` 分支合入需要的改动，运行 **Build MFABD2 prerelease**。
2. 等六个平台的包全部构建并发布为预发布，记下摘要中的六位提交号。
3. 二选一把编号交给本仓库的构建：
   - **推送**：在提交信息里单独写一行 `[mfaa:编号]`，放在发版标记的上一行，例如

     ```text
     fix: 某某修复

     [mfaa:9aa52b]
     [deploy-beta]
     ```

     无参数 `git commit` 打开的模板里已备好 `#[mfaa:六位提交号]`，删掉 `#` 填入编号即可。
   - **正式版（推标签）**：版号照旧由标签名指定，把 `[mfaa:编号]` 写进**附注标签的说明**：

     ```bash
     git tag -a v4.6.5 -m "[mfaa:9aa52b]"
     git push origin v4.6.5
     ```

     图形界面打标签时，在标签说明（message）里填同一行即可。标签说明里有标记时以它为准；
     说明为空或是轻量标签时，改读所标提交的标记。
   - **手动**：**Actions → install → Run workflow** 的 `mfaa_commit` 填入该编号，再按原有方式选择发布通道。
4. 以上都不写时完全沿用 `requirements.txt`。

编号必须恰好六位十六进制字符，允许前导零，大小写不限。推送分支时只看被推送的最新一个提交，
以 `[mfaa:` 开头的行才算标记（同一行后面可以接 `[deploy-beta]`）；`#` 注释掉的行、正文中间
顺带提到的不算。写错（没填编号、位数不对、同一段说明写了两个不同编号）时，在解析发布通道这一步
就失败，不会取消正在跑的同通道构建，也不会悄悄换回官方包。PR 构建一律用官方包。
它不修改客户端的“更新软件”行为。

自家版本必须来自 `sunyink/MFAAvalonia:mfabd2`，标签形如
`v2.16.3-mfbd2.g4e22d1`，并且必须是预发布。CI 会解析完整提交，检查标签所指提交、
六个平台附件、`fork-release.json` 中的大小与 SHA-256，以及解压后的
`mfaa-build.json` 平台和提交标记。不接受仅有源码而未出包的提交；找不到、编号有歧义、
附件不完整或来源不符时直接失败，不自动换回官方包。

内核探测和桌面打包使用同一份所选 MFAA。现有 `MFA_CORE_TAG` 覆盖与 Android UI
构建规则保持原有职责；本输入不把 MFAA Android shell 换入本项目的 Android 应用。
运行摘要记录实际客户端仓库、标签及完整提交，打包后的客户端保留来源标记供排查。
