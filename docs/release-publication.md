# 发布保护与恢复

完整版本统一通过 `install.yml` 发布：桌面六个平台、安卓和更新日志全部成功后，
`install-build.yml` 的发布作业才会创建草稿。公测、内测、普通 CI 与正式版共用这条保护路径，
版号生成及通道分类规则不变。

## 从草稿到公开

`scripts/release_guard.py` 使用 Python 3.11，在创建草稿前检查本地附件清单，并核对真实 Git tag
最终指向的 commit。`target_commitish` 字段相同不能代替这项检查；缺失 tag 会创建，已有错误 tag 会拦下。

草稿正文末尾保留一条隐藏 HTML 注释，记录仓库、提交、运行 ID、重跑次数及附件摘要。
后续上传和公开使用固定 Release ID。公开前再次核对归属、同 tag 唯一性，以及每个附件的
文件名、大小、GitHub 返回的 SHA-256 和上传完成状态；十个附件全部符合才设置 `draft=false`。

上传和清理共用按 tag 区分的并发组。同 tag 的受控作业不会同时修改草稿。
这不能阻止维护者在网页或其他工具里手动操作；检测到状态、归属或附件异常时会停止。
编辑发布说明时应保留隐藏的 `mfabd2-release-guard:v1` 注释，它是恢复与清理所需的记录。

## 失败、取消与重跑

- 上传失败或取消：当前发布作业尝试删除本次运行拥有的草稿；Git tag 保留。
- 当前作业被终止而未完成清理：默认分支上的 `release-cleanup.yml` 接收 `install` 结束事件，
  核实失败运行、提交和重跑次数，取得同 tag 的并发锁后重新读取归属，再删除仍属于该次失败运行的草稿。
- 旧清理任务晚到：新重跑已接管的草稿不会被旧任务删除；公开 Release 也不会被清理。
- 重跑遇到旧草稿：仅接管身份一致且原拥有者已结束的草稿；活动运行和没有记录的旧草稿需要人工排查。
- GitHub 已公开但响应丢失：重新查询确认结果。再次运行时按原记录校验公开版，不覆盖附件；
  重打包导致 ZIP 时间戳变化也不会改写已经公开的版本。
- 公开版附件不完整或内容变化：拦下并要求人工排查，不自动补写公开附件。

自动清理仅处理带本脚本有效记录的草稿，不清扫历史或手工草稿，也不删除 tag。
独立清理工作流自身失败时仍需人工查看 Actions，不能把它视为绝对不会留下草稿的保证。

## 镜像与 Android

镜像派发已拆为独立 `mirror` 作业。失败后可只重跑失败作业；它先只读核验公开 Release，
再派发镜像工作流，不重新上传公开附件。若第一次派发成功而第二次失败，重跑可能再次派发第一个镜像任务。

`android.yml` 保留 APK 单独构建与 Actions 产物下载。旧 `publish=true` 参数会在构建前拒绝，
防止绕过完整发布检查直接给已有 Release 附加文件；主流程使用的 `release_build=true` 不受影响。

## 上线与验证

手动派发执行所选分支自己的工作流，修改 main 不会自动保护其他发版分支。
应先推送 main，让默认分支具备独立清理工作流，再推送同一修补到实际发版分支。
旧提交的既有运行重跑仍使用旧工作流，不能当作修补上线后的验收。

本地检查：

```powershell
py -3.11 -B scripts/verify_release_guard.py
py -3.11 -B scripts/verify_release_channels.py
```

测试使用模拟 GitHub 接口，不会创建或修改线上 Release。它们覆盖发布状态转换、失败恢复和清理归属，
不能替代上线后真实上传、公开、镜像派发及取消场景的验收。
