# 钓鱼模块开发说明

面向要接手或改动钓鱼功能的开发者。讲清楚模块的边界、对外接口、参数在哪调，以及哪些东西是坏的、哪些是死的、为什么还留着。

用户向的使用说明不在这里 —— 那是 GUI 里的任务描述。

## 模块在做什么

一句话：**导航到钓鱼点这段用 Pipeline JSON 编排，钓鱼小游戏那段用 Python 实时闭环，卖鱼再交回 Pipeline。**

小游戏必须走 Python，是因为它要在一局之内连续截图、算游标什么时候到达目标区、提前若干毫秒下点击 —— 这是逐帧的预测控制，Pipeline 的节点跳转粒度做不了。

## 文件构成

| 文件 | 内容 |
| --- | --- |
| `assets/resource/base/pipeline/Fishing.json` | 42 个节点，整个模块的全部 Pipeline 逻辑（含卖鱼） |
| `assets/resource/pc/pipeline/Fishing.json` | PC 端覆盖，只有 2 个节点 |
| `agent/fishing_agent.py` | 小游戏闭环 + 唯一的 CustomAction |

`agent/main.py` 里一行 `import fishing_agent` 完成注册，没有别的挂载点。

卖鱼原先是独立的 `SellFish.json`，已并入 `Fishing.json`：它不是独立 task（`interface.json` 里没有它的 entry），按"一个 json = 一个 task"的切分依据本就不该单独成文件。

## 一、对外接口

### 1. interface.json 接线

只有一个 task：

```text
name:       [半自动]自动钓鱼
entry:      Fishing_Entry
controller: ["Adb"]
```

注意 `controller` **只声明了 Adb**。PC 端目前没有可用的钓鱼通路（详见"已知缺陷"）。

两个 option：

| option | 类型 | 覆盖点 | 做法 |
| --- | --- | --- | --- |
| 钓鱼地点 | select | `Fishing_MapNavigate.next` | 三选一改路由，决定走哪个 `Fishing_EnterFishingSpot_*` |
| 目标次数 | input | `Custom_Fishing_Task.custom_action_param.max_count` | `{目标钓鱼条数}` 占位符注入 |

还有一个 `周常钓鱼` option **不属于这个 task**，它只碰 `Weekly_Flishing_Hub.enabled`。

### 2. 跨文件的入口与出口

外部进入本模块的三条路：

| 来源 | 入口节点 | 场景 |
| --- | --- | --- |
| `interface.json` | `Fishing_Entry` | 用户手动跑 |
| `Weekly.json` | `Fishing_Entry` + `Custom_Fishing_Task` | 周常钓 1 条 |
| `Daily.json` | `Fishing_InMap_TalkSkip` / `_TalkSkip_Ck` | 借用对话快进 |

`Fishing_Entry` 是唯一的正式入口，本身不做识别，只做三件事：

```json
{
    "anchor": {"MainMenu_GoFishing": "Fishing_InFishingNet"},
    "next": ["Daily_Busin_Hub_Post", "Fishing_Already_Setsail", "[JumpBack]Global_ToHomePage"]
}
```

`anchor` 是 object 形式，作用是**定义**锚点 `MainMenu_GoFishing` 绑到 `Fishing_InFishingNet`。`Daily.json` 与 `Weekly.json` 各有一处 `[Anchor]MainMenu_GoFishing` 在等这个绑定 —— 换句话说，日常经营子菜单里"去钓鱼"那个跳转点落到哪，是由 `Fishing_Entry` 在运行时决定的。没跑过 `Fishing_Entry` 时锚点为空，`[Anchor]` 直接落空跳过。

Weekly 那条路更绕，用了两次 `PatchPipeline`：

1. 改 `Custom_Fishing_Task` 的 `max_count` 为 3、`next` 为 `[Anchor]Weekly_Fishing`，让钓完能回周常自己的收尾；
2. 给 `Daily_Busin_SubMenu.next` 挂上 `[Anchor]MainMenu_GoFishing`；
3. 然后才 `next: ["Fishing_Entry"]`。

> **改 `Custom_Fishing_Task` 前必读**：它的 `next` 在周常场景下是被外部注入的。如果给它写死一个 `next`，周常那条链会断。只看 `next` 字段会以为它是个孤立叶子节点 —— 模块耦合必须连 `custom_action_param` 与 patch 载荷一起看。

本模块引用的外部节点：

| 来源文件 | 节点 |
| --- | --- |
| `Global.json` | `Global_ToHomePage`、`Global_WaitingForLoading` |
| `Daily.json` | `Daily_Busin_Hub_Post`、`Daily_Square_Hub`、`Daily_FantasiaSquare`（patch 目标） |
| `Arbitrage.json` | `Arbitrage_NviGuide_Onfoot_Loop`、`Arbitrage_NviGuide_CKMsgBox_Ocr` |
| `Battle.json` | `QuickHunt_MIniMap_locErr` |

`Fishing_Move_*` 那一组（走路去码头）**整个是借 Daily 和 Arbitrage 的现成设施拼的**：`Fishing_Move_Hub` 用 `PatchPipeline` 改 `Daily_FantasiaSquare.next` 指回自己再跳进 `Daily_Square_Hub`；`Fishing_Move_NviGuide_CKMsgBox_Ocr` 用 `Or` 复用套利模块的弹窗识别。这块是模块里耦合度最高的地方，改动最容易波及别的模块。

### 3. JSON 与 Python 的契约

唯一的注册点：

```python
@AgentServer.custom_action("FishingAction")
class FishingAction(CustomAction):
    def run(self, context, argv) -> bool
```

对应 `Custom_Fishing_Task` 的 `"custom_action": "FishingAction"`。**没有注册任何 CustomRecognition**，所有识别都走 Pipeline 节点。

`custom_action_param` 认三个键：

| 键 | JSON 里给了吗 | 缺省行为 |
| --- | --- | --- |
| `max_count` | 是（`100`） | 缺省为 1；interface 的"目标次数"可覆盖；Weekly 打 patch 改成 3 |
| `sell_interval` | 否 | 回落到 `Fishing_Minigame_Strategy.attach` |
| `max_seconds` | 否 | 按 `max(120, max_count × 120)` 估算 |

`max_seconds` 是总时长硬上界，用来兜住 `Casting_Rod` 与 `Move_Forward` 的自环（见"已知缺陷"）。它只在轮与轮之间生效，拦不住单次 `run_task` 内部的阻塞。

Python 反向调用 Pipeline 的节点：

| 节点 | 调用方式 | 用途 |
| --- | --- | --- |
| `Detect_Took_Bait` | `run_recognition` | 判鱼上钩（感叹号） |
| `Rec_FishMinigame_Cursor_Clr` | `run_recognition` | 进度条游标位置 |
| `Rec_FishMinigame_BlueZone_Clr` | `run_recognition` | 蓝区 |
| `Rec_FishMinigame_YellowZone_Clr` | `run_recognition` | 黄区 |
| `Casting_Rod` | `run_task` | 抛竿并等鱼上钩，每轮一次 |
| `SellFish_Start` | `run_task` | 卖鱼，攒够 `sell_interval` 条时触发，结束时再兜一次 |

这也是钓鱼与卖鱼两段的真正接缝：卖鱼在 Pipeline 层被 `Fishing_Start.next` 引用一次，在 Python 层被 `run_task` 引用两次。

## 二、节点分布

42 个节点按职能分六组：

| 组 | 节点 | 说明 |
| --- | --- | --- |
| 入口与路由 | `Fishing_Entry`、`Fishing_MapNavigate`、`Fishing_EnterFishingSpot_×3` | `MapNavigate` 是空壳，只有 `next`，专供 interface 覆盖 |
| 进场链 | `Fishing_InFishingNet` → `InMap` → `MapNavigate` → `SetSail` → `Start`，旁路 `Already_Setsail`、`BusinReward` | 唯一写了 `focus` 成功/失败双分支的是 `InFishingNet` |
| 打断处理 | `Fishing_InMap_TalkSkip`、`_TalkSkip_Ck`、`_TutorialSkip` | 被 Daily 和 pc 包共同引用，模块里复用度最高 |
| 走路去码头 | `Fishing_Move_Hub`、`_SandBoxAct`、`_NviGuide_Butt`、`_NviGuide_SubOcr`、`_NviGuide_CKMsgBox_Ocr` | 全部外联，见上文 |
| 钓鱼动作 | `Casting_Rod`、`Move_Forward`、`Detect_Took_Bait` | 前两者互为 `next` / `on_error`，构成自环 |
| 小游戏 | `Custom_Fishing_Task`、`Rec_FishMinigame_×3`、四个 `Fishing_Minigame_*` 配置节点 | 识别节点不进管路，配置节点 `enabled: false` |

卖鱼是一条无分叉线性链：

```text
SellFish_Start (max_hit:1, 点卖鱼图标)
  → SellFish_Shop (确认在商店)
      ├→ SellFish_Step2_NoFish  (没鱼 → 直接 End)
      └→ SellFish_SellModOn → SwichAll → ActionButt → ActionButt_Ck → End
```

图中省略了 `SellFish_` 前缀。其中 `SellFish_SwichAll`、`SellFish_ActionButt`、`SellFish_ActionButt_Ck` 三处用了自引用重试（把自己放在 `next` 末位）。`SellFish_End` 不写 `next`，是退栈点。整条链没有任何 `on_error`，全部走默认的静默出栈。

### pc 包覆盖

PC 端只覆盖两个节点，都是对话快进相关：`Fishing_InMap_TalkSkip` 的 `roi`，以及 `_TalkSkip_Ck` 的 `expected`（补繁体「確認」）。

## 三、参数体系

小游戏的可调参数全部落在 Pipeline 节点的 `attach` 上，**改值一律改 JSON，不要动 Python**。Python 侧的默认值只在"节点缺失 / 键缺失 / 值非法"时兜底，正常运行不生效。

四个节点都在 `base/pipeline/Fishing.json`，都是 `enabled: false`（不参与流程，但 `attach` 照样读得到）。

### Fishing_Minigame_Data — 机制常量

由游戏本身决定，与设备和端无关，三端共用。

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `cursor_speed` | 4.2 | 游标移动速度（px/帧） |
| `blue_shrink` | 0.83 | 蓝区单边向心收缩速度（px/帧） |
| `cursor_half_cycle` | 88 | 游标单程帧数，一个完整往返是它的 2 倍 |
| `ref_fps` | 60.0 | 上面两个"每帧"速率所基于的帧率 |
| `minigame_seconds` | 17 | 单局时长上界，超时即收尾 |

**前四项互相咬合**，共同决定"游标此刻在哪、朝哪走"的推算。改任一项都要连带复核其余三项。

### Fishing_Minigame_Timing — 时序补偿

决策层到画面真正生效之间的时间差，与设备和控制器性能相关，per 端可覆盖。

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `click_lead` | 0.27 | 点击提前量（秒），判定"还追不追得上目标区""蓝区归零前来不来得及"时预留的余量 |
| `input_comp` | 0.045 | 输入链路延迟（秒），直接从等待时长里扣 |
| `cursor_reset_wait` | 0.6 | 点击后游标复位等待（秒） |
| `after_cast` | 0.2 | 抛竿命中后进入小游戏的等待（秒） |
| `after_catch` | 3.0 | 上鱼后结算动画等待（秒） |

调参方向：**点击总是偏早就调小 `click_lead` 与 `input_comp`，总是偏晚就调大。**

### Fishing_Minigame_Strategy — 策略阈值

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `sell_interval` | 30 | 累计钓到几条触发一次自动卖鱼 |
| `wait_cap` | 5.0 | 单次等待时长上限（秒），算出超过此值视为游戏状态已变，放弃本次点击 |
| `blue_min_width` | 5 | 蓝区预测宽度下限（px），预测到达时窄于此值则不点 |

`sell_interval` 的优先级是 **`custom_action_param` > 节点 attach > Python 默认**。

### Fishing_Minigame_Settle — 结算点击点

上鱼后关结算界面的点击点。Python 读它的 `target` 后自行点击，不走 `run_task`，所以它不写 `recognition` / `next` —— 它只作为该坐标的唯一出处存在，不要挂进管路。

### 两处不在 attach 里的坐标

进度条左右边界和拉杆点**不另设参数**，直接从既有节点反查：

```python
progress_roi = context.get_node_data("Rec_FishMinigame_Cursor_Clr")["roi"]
bar_left, bar_right = progress_roi[0], progress_roi[0] + progress_roi[2]

cast_target = context.get_node_data("Casting_Rod")["target"]
```

理由：这两个数值本就必须与识别 ROI 严格一致 —— 游标位置是在那个 ROI 里测出来的，边界对不上就会算错时机。做成两个可以各自修改的参数，等于把已经发生过的 bug 制度化（改造前 Python 里写的是 484/858，而 ROI 是 480/863，已经漂了）。

### per 端覆盖怎么写

`attach` 是按 key 字典合并的，所以 pc 包只需要写差异项。例如 PC 端输入链路更快：

```json
{
    "Fishing_Minigame_Timing": {
        "attach": {
            "input_comp": 0.02
        }
    }
}
```

其余键仍取 base 的值。目前 pc 包**还没有**建这类覆盖。

## 四、已知缺陷

### 1. Casting_Rod 与 Move_Forward 构成自环

两者互为 `next` / `on_error`。框架自带的 "error handling loop detected" 保护**不会触发**，因为每次命中节点都会重置 `error_handling`。

目前靠 Python 侧的 `max_seconds` 兜住，但那只在轮与轮之间生效，拦不住单次 `run_task` 内部的阻塞。真正的修法是切断 Pipeline 自环，尚未做。

### 2. PC 端没有可用通路

task 的 `controller` 只声明了 `Adb`，pc 包只剩 2 个 ROI 覆盖。上一代的 PC 钓鱼实现（`NiceBoat` / `Cast` / `Bite` / `TugOfWar` 等 19 个节点，一整套纯 JSON 的拉锯战逻辑）已随 NT 分支同步被移除 —— 它们与现行的 `Custom_Fishing_Task` 链路零引用，是死代码。

要做 PC 支持是从零开始，不是修补。

### 3. iOS（PlayCover）同样未适配

见 [PlayCover 适配指南](PlayCover适配指南.md)，钓鱼是明确排除在外的。

### 4. 文件头 docstring 与实现不符

`fishing_agent.py` 开头写着 "Defaults assume the game runs at 1920x1080"、"all points are scaled at runtime based on the current screenshot resolution"。**两句都不成立**：代码里没有任何缩放逻辑，坐标基准是项目统一的 1280×720。这是从独立版移植时留下的，读代码时不要被它误导。

### 5. 日志方式与项目规范不一致

`CONTRIBUTING.md` 要求 `agent/` 下用 `mfaalog`，但 `fishing_agent.py` 全部是裸 `print`，靠 `warn:` / `error:` 前缀被 MFAAvalonia 的日志协议识别。这是移植时留下的偏差，改动本文件时沿用现状即可，要统一到 `mfaalog` 应当单独做一次，不要混在功能改动里。

注意裸 `print` 的两个已知代价：无前缀的行进不了 GUI 日志墙；`stdout` 是与 UI 的管道，往里打大对象（如整个 `RecognitionDetail`，含 `raw_image` 等 ndarray）会拖慢整个流程 —— 这类打印已经清过一轮，别再加回去。

## 五、死代码清单

以下东西**确认无任何调用方**，但按约定保留未删 —— 它们大多是给未来 iOS / PC 适配留的余地。改动这块前先读这张表，不要把它们当活代码去理解。

| 位置 | 东西 | 为什么死的 |
| --- | --- | --- |
| `fishing_agent.py` | `long_press()`、`swipe()` | 抛竿实际走 Pipeline 的 `Casting_Rod`（LongPress 动作） |
| `fishing_agent.py` | `wait_for_fish()` | 等鱼上钩走 `Casting_Rod` → `Detect_Took_Bait` |
| `TimingCfg` | `wait_fish_interval` | 只被 `wait_for_fish` 用 |
| `TimingCfg` | `input_delay` | 从未被读过，实际生效的是 attach 的 `input_comp` |
| `CoordCfg` | `minigame_area` | 零引用 |
| `Fishing.json` | `Detect_CountDown`、`_Green`、`_Red` | 三个零入度节点，Python 与 JSON 都不引用 |
| `Fishing.json` | `Reco_Minigame_Total_Time` | 唯一的引用处在 `play_minigame` 里被注释掉了 |
| `Dummy.json` | `Fishing_NiceBoat` | 上一代 PC 实现留下的占位定义 |
| `pc/image/` | `UI_BoatToDock.png` | 随上一代 PC 实现失去引用 |

`Reco_Minigame_Total_Time` 那处值得说明：它本来是要 OCR 出小游戏的实际总时长，替换掉写死的 `minigame_seconds`。恢复它是个明确的改进方向。

## 六、待办：时序参数的动态测量

现在这套换算链建立在两个**测不到的假设**上：游戏跑在 60 FPS、游标每帧走 4.2 px。这两个数一旦不成立（掉帧、高刷屏、模拟器渲染差异），后面所有时间计算全错，而且错得没有任何反馈。

`Fishing_Minigame_Timing` 的存在就是为这件事预留的落点。计划分三层，按风险从低到高：

### L1 · 消灭 FPS 假设

不测帧率，改测**游标像素速度（px/秒）**：连续两帧截图各记一次 `time.monotonic()`，用 Δx / Δt 直接得速度。

这一步同时废掉 `cursor_speed`、`ref_fps`、`cursor_half_cycle` 三个硬编码 —— 方向反转也能从速度符号变化里读出来，不必再靠帧号推算。

**这条最值得先做。** 现在的 `_get_cursor_direction_from_frame` 是拿 `int((now - start) × 60)` 反推帧号的，只要掉一次帧，方向判断就会持续错到本轮结束。

### L2 · 截图延迟自测

`post_screencap()` → `get()` 的耗时已经可测（`tap()` 里已经在测点击耗时，只是打印完就丢了）。取滑动窗口中位数，作为"这张图已经是 N 毫秒前的画面"的补偿量，比固定的 `input_comp` 诚实。

### L3 · 输入到生效延迟的闭环标定

最难，因为没有现成的 ground truth。可行路径：点击后连续高频截图，检测游标复位的那一帧，反推 `post_click` 到画面变化的真实延迟；每轮小游戏开头标定一次。

做到这一步，`Fishing_Minigame_Timing` 的 attach 值就降级为**初值和上下界** —— 测出来的值落在区间内才采信，离谱就不采信。

三层的共同约定是：**JSON 提供初值与合法区间，运行时测量值在区间内才覆盖。** 这样 ADB / PC / PlayCover 各端不必各写一套常量，也是钓鱼多端适配的地基。
